# 교통 노선 검색 연결

버스는 지역 → 승차·하차 정류장 이름/번호 검색 및 선택 → 해당 방향으로 연결되는 노선 선택으로 저장한다. 같은 이름의 맞은편 정류장은 번호로 구분한다. 지하철도 승차·하차역 검색 후 같은 노선을 선택한다. 현재는 환승 없는 구간만 지원하며 지하철은 호선별 역을 구분해 선택한다. 별칭만 자유 입력한다. 기존 직접 입력 기록은 그대로 조회·별칭 수정·삭제할 수 있고, **노선 변경**으로 API 노선을 다시 선택한다.

## 처음 준비할 것

1. [공공데이터포털](https://www.data.go.kr/)에 로그인한다.
2. [국토교통부 TAGO 버스노선정보](https://www.data.go.kr/data/15098529/openapi.do)와 [국토교통부 TAGO 지하철정보](https://www.data.go.kr/data/15098554/openapi.do) 각각에서 **활용신청**을 한다. 정류장 우선 검색에는 [TAGO 버스정류소정보](https://www.data.go.kr/data/15098534/openapi.do), 실시간 버스 도착에는 [TAGO 버스도착정보](https://www.data.go.kr/data/15098530/openapi.do)도 필요하다.
3. 마이페이지의 활용 현황에서 사용할 서비스가 모두 승인되었는지 확인하고 인증키를 복사한다. Decoding 키를 권장하며 Encoding 키도 처리한다. 발급·승인 직후에는 제공기관 반영 시간이 필요할 수 있다.
4. 프로젝트 루트에 `.env.transit.local`을 만들고 아래 내용을 넣는다. 이 파일은 Git에서 제외된다. 실제 키를 채팅·README·프런트엔드 환경변수에 넣지 않는다.

```dotenv
TAGO_SERVICE_KEY=발급받은_인증키
TRANSIT_ALLOWED_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
TRANSIT_PORT=4191
```

Node 22.9 이상에서 아래 명령 하나로 웹과 교통 조회 서버를 함께 실행한다.

```sh
npm run dev
```

조회 서버만 별도로 실행할 때는 `npm run transit:server`를 사용한다. `npm run dev`는 기존 조회 서버가 있으면 재사용하고, 직접 띄운 조회 서버만 종료 시 함께 정리한다. 직접 띄운 조회 서버가 예기치 않게 종료되면 웹도 종료해 불완전한 실행 상태를 남기지 않는다.

개발 화면은 기본으로 `http://127.0.0.1:4191`에 연결한다. `/planner/routes/` → **교통 노선 추가**에서 버스와 지하철을 각각 검색한다. 키 없이 실행해도 서버는 뜨지만 화면에 연결 준비 상태를 표시하며 가짜 목록은 제공하지 않는다.

기존 `4190` 포트는 Fetch에서 차단되므로 사용하지 않는다. 이전 로컬 설정을 옮길 때는 `.env.transit.local`의 `TRANSIT_PORT`도 `4191`로 변경한다.

## 배포와 Android

현재 Next 앱은 정적 export이므로 런타임 Route Handler를 추가하지 않고 별도 Node 서버를 쓴다. 조회 서버는 loopback에 바인딩한다. 운영에서는 HTTPS 리버스 프록시 뒤에 배치하고, 프록시에서 요청량 제한을 적용한다. `TRANSIT_ALLOWED_ORIGINS`에는 실제 웹 origin과 Android WebView origin만 지정한다. CORS 자체는 사용자 인증이나 사용량 제한을 대체하지 않는다.

웹/APK를 빌드할 때 공개 조회 서버 주소를 지정한다. 실제 서비스키는 서버 환경변수에만 둔다.

```sh
NEXT_PUBLIC_TRANSIT_API_URL=https://your-transit-server.example npm run build
# Android도 동일한 환경변수로 npm run build:android 실행
```

운영 주소 없이 빌드한 화면은 연결 준비 상태를 보여 준다. 기존 APK에는 변경 사항이 자동 반영되지 않으므로 서버 연결 후 새 APK를 빌드해야 한다. 개인 PC의 loopback 주소는 휴대폰에서 사용할 수 없다.

## API와 데이터 처리

- 버스: `BusRouteInfoInqireService/getCtyCodeList`, `getRouteNoList`, `getRouteAcctoThrghSttnList`. 정류장 검색은 `BusSttnInfoInqireService/getSttnNoList`, 승차 정류장의 후보 노선은 `getSttnThrghRouteList`로 조회한다. 후보별 경유 정류장 순서·방향을 검사해 하차 정류장까지 가는 구간만 반환한다. 후보 조회 장애는 부분 결과를 성공으로 표시하지 않는다.
- 버스 도착: `ArvlInfoInqireService/getSttnAcctoArvlPrearngeInfoList`. 승차 정류장의 도착 정보를 노선 ID로 필터링한다. 서버 캐시는 10초이며 같은 승차 정류장의 카드들은 하나의 요청과 5초 클라이언트 캐시를 공유한다. 화면은 표시 중 30초마다 갱신하며 마지막 조회 시각을 보여 준다. 정보 없음·승인 필요·연결 장애를 구분한다. 지하철 실시간 도착은 미연결이며 시간표를 실시간으로 표시하지 않는다.
- 지하철: `SubwayInfo/GetKwrdFndSubwaySttnList` (대문자 `G`). 역명 조건을 생략해 전체 페이지를 읽고 노선별로 역 목록을 묶는다. 숫자 호선명은 여러 도시가 공유하므로 실제 응답의 역 ID 접두어로 광주·부산·대구·대전·수도권을 구분한다. 수도권의 공동 운영 구간은 합친다. 이 API는 선로 순서를 주지 않으므로 역은 가나다순으로 표시한다. 환승 경로 계산은 하지 않는다.
- 제공 도시 목록에서 지역을 고르며 광주광역시가 있으면 기본 선택한다. TAGO 미제공 도시·노선은 표시되지 않는다.
- 단건 객체·빈 결과·페이지 분할·XML 인증 오류를 구분한다. 전체 조회가 성공한 결과만 30분 캐시하고 동시 동일 요청은 공유한다. 중간 페이지 실패 시 부분 결과를 완전한 목록으로 표시하지 않는다.
- 버스 정류장은 상하행·순번을 유지한다. 동일 정류장 재방문도 서로 다른 선택 항목으로 처리하며 같은 방향의 후속 정류장만 하차 선택을 허용한다.
- 저장 필드 `transit`에 공급자, 노선 ID, 도시, 정류장 ID 및 방향·순번이 포함된 선택 키를 보존한다. 기존 `title`, `from`, `to`, `alias`는 호환된다.

## 검증

`npm run test:transit`은 공공 API 형식의 테스트 응답으로 페이지·캐시·오류·선택 구간·서버 검증을 확인한다. `npm run build`는 정적 빌드와 TypeScript를 검사한다. 테스트 응답은 실제 서비스 목록에 쓰지 않는다.

2026-11-12 두 서비스 승인과 서버 전용 키 설정을 완료했다. 실 API로 지역 138개, 지하철 37개 노선(광주 1호선 20개 역)을 조회했다. localhost 화면에서 광주 버스 `03` 검색, `급행03`의 첨단공영차고지 → 광주종합버스터미널 선택, 광주 1호선의 광주송정역 → 상무 선택 및 저장 버튼 활성화를 확인했다. 사용자 기록을 추가하지 않았으므로 실제 저장·재열기와 모든 지역의 개별 노선은 이번 연결 검증에 포함하지 않았다. 운영 웹·APK 연결은 별도 HTTPS 조회 서버 배포가 필요하다.

2026-11-12 정류소정보·버스도착정보도 추가 신청하여 두 건 모두 승인됐다(만료일 2028-11-12). 정류소 이름 검색으로 광주종합버스터미널의 두 방향 정류장(2001·2002)을 확인했고, 정류장 ID KJB110에서 급행03(KJB45)의 실제 도착예정시간·남은 정류장 수가 조회됐다. 인증키는 기존 서버 전용 설정을 사용한다. 변경한 검색 흐름의 테스트 17개와 정적 빌드가 통과했다. 모바일 화면에서 광주종합버스터미널(2002) → 경신여고(4434)를 선택해 26개 구간을 조회하고, 급행03 선택과 실제 도착 예정 시간·남은 정류장 수 표시 및 저장 버튼 활성화를 확인했다. 검색 결과가 많은 경우 카드 높이를 유지한 채 스크롤하도록 검증했다. 사용자 기록을 추가하지 않았으므로 실제 저장·재열기는 이번 검증에 포함하지 않았다.
